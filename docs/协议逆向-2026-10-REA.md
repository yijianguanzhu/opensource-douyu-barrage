## 2. loginreq（源码级验证 ✅）

网页版构造位置：`room_common_*.js` 模块 `9b112`（ConnectServer.userLogin + gatewayLogin）。

```
type@=loginreq/roomid@=%d/
dfl@=<屏蔽配置，形如 sn@AA=105@ASss@AA=1>/
username@=%s/password@=%s/ltkid@=%d/biz@=%d/stk@=%s/
devid@=%s/ct@=0/pt@=2/cvr@=0/tvr@=7/apd@=/jwt@=%s/
rt@=%d/vk@=%s/
ver@=20220825/aver@=218101901/dmbt@=%s/dmbv@=%s/
```

要点：
- `password` 取 cookie `auth_wl`（访客为空）、`jwt` 取 cookie `dmjwt_token`（可为空）。
- `devid`：网页登录后服务器会下发新的 acf_devid（本例 cookie 原 `417fb4ae...` → 线上帧 `ed729687...`，与 URL 参数 `dyshid` 同源）；Java 直连用 cookie 原 acf_did 亦可正常登录。
- **vk 算法（gatewayLogin 源码逐字提取）**：
  ```js
  vk = md5( rt + "r5*^5;}2#{$XF[h+;'./.Q'1;,-]f'p[" + devid )
  ```
  秘钥 32 字节，**网页版至今仍用此老秘钥**。已用线上帧离线验证：
  `rt=1793203263, devid=ed72968709ab782c8d4e37b400021701`
  → `md5(...) = 24bbf1b7cb83e675b17637d9bf3c0c98`，与线上 `vk@=` 逐字节一致。
- `rt` 与 `vk` 必须同一秒：网页版同一个 `v()` 值既写入 rt 也参与 vk 计算。

## 3. keeplive（新格式，2026-10 复核）

```
type@=keeplive/vbw@=<player bytecount>/cdn@=<cdn>/tick@=%d/kd@=%s/alg_ver@=1.0/key_ver@=1.1/sig@=%s/
```

- 老格式（无 `alg_ver/key_ver/sig`）服务器已不响应，约 30 秒后踢线——已实测。
- `alg_ver@=1.0`：WebEncrypt.sign 内的常量 `"1.0"`。
- `key_ver@=1.1`：`getEncryption` 响应里 `cpp.heartbeat.key_ver`。
- **sig 签名值已线上对拍验证（14/14 命中，算法见 §4）**：网页版每次心跳都携带真实签名
  （`l = md5(rand_str + cpp.heartbeat.key)`，`sig = md5(l + key + rid + did + tick)`，rand_str 取最近一次 getEncryption 响应）。
  本库实测**发送空串 sig 服务器当前也接受**（存活 >100s 且心跳均有响应）——即服务器对普通房间暂未强制校验网关签名，
  但这不代表网页发空串；若未来强制校验，按 §4 公式实现即可。
- 心跳间隔 30s（`keepLiveTime`）。

## 4. 网关加密签名（WebEncrypt，线上对拍验证 ✅；当前普通房间未强制校验）

源码：`room_common_*.js` 模块 `1a0dd`（WebEncrypt 类）+ `df2d6`（getLoginParam/getHeartbeatParam）。

握手流程（loginres 后触发；**实测普通房间同样发生**——3487376 一个 80 秒会话内 `livreq` 发送 14 次、
仅 2 次收到 `livres`、随后 2 次 `lsigreq`，客户端对未响应的 livreq 持续重试）：
1. `livreq`：`{type:"livreq", alg_ver, key_ver}` ← `getLoginParam({type:"login", ts, did, rid})`
2. 服务器回 `livres`：带 `nonce`、`its`（实测均为 `its@=0`）
3. `lsigreq`：`{type:"lsigreq", sig, ts}` ← `getLoginParam({type:"login", ts, did, rid, rand_str:nonce, enc_time:its})`

**签名算法（sign 方法源码还原 + 线上对拍逐字节验证 ✅）**：
```
输入: type, ts, did, rid, rand_str, enc_time, key = getEncryption 响应
login:     k = key.cpp.danmu.key,     kv = key.cpp.danmu.key_ver
heartbeat: k = key.cpp.heartbeat.key, kv = key.cpp.heartbeat.key_ver

l = rand_str
repeat enc_time 次:  l = md5(l + k)          // md5 迭代
sig = md5(l + k + rid + did + ts)             // 末轮再拼上 rid+did+ts
alg_ver = "1.0", key_ver = kv
```
（`stream` 类型用于播放流签名 `/lapi/live/getH5PlayV1`，`i = rid+ts`，另有 `enc_data` 机制。）

密钥获取：`GET /wgapi/livenc/liveweb/websec/getEncryption?did=<devid>`。
网页版**每 ~25-30 秒重新拉取一次**该接口（每次响应 `rand_str` 不同），每跳 keeplive 的 sig 都用最新一次的 `rand_str` 计算。

**验证状态（2026-10-29 更新，线上对拍 ✅）**：此前「未获得线上 sig 样本」的结论已过时，现为全量验证：
- **lsigreq：3/3 全部命中**（两个会话）。`its@=0` → md5 迭代 0 次，`sig = md5(nonce + cpp.danmu.key + rid + did + ts)`。
  样本：rid=3487376, did=f80549588eeaac4466927d4300011701, nonce=PVzgRC4fIk, ts=1793191325 → sig=42c90f3e6c3933f07bd5f281e364aa08 ✅
- **keeplive：14/14 全部命中**（同会话）。`l = md5(rand_str + cpp.heartbeat.key)`（enc_time=1），
  `sig = md5(l + cpp.heartbeat.key + rid + did + tick)`。样本：did=ed72968709ab782c8d4e37b400021701, tick=1793261841 → sig=6eb41918caa6968a7e15f195ca251537 ✅
- **cpp 密钥全局共享（非按设备/账号发放）**：同日两个账号（uid=237818543 / uid=387277437）会话拿到的
  `cpp.danmu.key`/`cpp.heartbeat.key` 完全相同（`MKy68tTD41YmvJZwgVKQ` / `68rdVozmeLwhgPoaGABH`）。
- **服务器当前不强制校验**：本库整体跳过 livreq/lsigreq 握手、keeplive sig 发空串，
  登录/发弹幕/心跳响应均正常（100 秒+存活实测）。若未来强制校验，按上式实现即可（密钥从 getEncryption 取）。

## 5. chatmessage（发送弹幕）

线上帧格式（2026-10 抓包）：
```
pe@=0/content@=%s/col@=0/type@=chatmessage/dy@=<devid>/sender@=<uid>/
ifs@=0/nc@=0/dat@=0/rev@=0/tts@=%d/admzq@=0/cst@=%d(毫秒)/
```

发送前预处理（模块 `b3f08` 的 chatmessage 钩子，源码还原）：
1. 客户端黑词检查（`hasBlackWord`，命中本地直接拦截 error code 60）。
2. `#ZQ` 前缀（platformGroup=5 足球房间）剥离并把 `admzq` 置 1。
3. **`content` 里反斜杠 `\` → 全角 `＼`，连续两个 `＼＼` 再合并为一个**（`replace(/\\/g,"＼").replace(/＼＼/g,"＼")`）。
4. `tts` = 播放器 SEI 时间（秒，无播放器场景可置 0）；`cst` = 客户端毫秒时间戳。

服务器回执 `chatres`：`res@=391` 为正常 ACK（`cd@=` 冷却秒数、`txt@=` 回显内容）。

**参数完整性审计（2026-10-29）**：与网页真实发送成功帧逐字段对拍——
```
pe@=0/content@=主播加油/col@=0/type@=chatmessage/dy@=f80549588eeaac4466927d4300011701/
sender@=387277437/ifs@=0/nc@=0/dat@=0/rev@=0/tts@=0/admzq@=0/cst@=1793191383275/
```
项目 `pushMessage` 模板 13 个字段全部对齐、顺序一致、**无遗漏**；填参逻辑核对无误（转义链顺序、`dy` 与登录
`devid` 同源、`cst` 为 13 位毫秒）。网页发普通文本弹幕就是这 13 个字段，老协议的 `dfl/ic` 等字段新版帧已不存在。

## 6. STT 序列化器（源码还原）

模块表（`room_common_*.js` @1961089）：
```
encode(obj):
  对每个 key/value:
    escape: '/' → "@S"，'@' → "@A"      // key 与 value 都转义
    拼接: escape(key) + "@=" + escape(value) + "/"
二进制帧: len(4,LE) + len(4) + code(2, 发送689/接收690) + 保留(2) + payload + '\0'
```

## 7. 其它协议要点（对照源码复核）

- `joingroup`：`{type:"joingroup", rid, gid}`（gid 默认 1，弹幕分组）。
- `h5ckreq`：`{type:"h5ckreq", rid, ti:window.vdwdae325w_64we}` —— `ti` 是一个混淆的全局运行时令牌（由字符串解密函数 `u.default(256042,"9f4f...")` 一类机制生成），无副作用、非必需，Java 实现可保留旧格式或省略。
- `logout`：`{type:"logout"}`。
- 多条 wsproxy 并发连接是网页版常态（页面同时开 3~5 条推送连接，各自独立 login/keeplive）。

## 10. 缺陷审计与修复（2026-10-29，对照网页版源码行为）

| # | 缺陷 | 危害 | 修复 |
|---|---|---|---|
| 1 | 心跳仅在收到 `pingreq`/`mrkl` 时启动，但网页版是 **loginres 后立即自调度**（源码 `userLoginResponse → subscribeStream(keepLive)`），且新协议下推送连接服务器不主动下发 pingreq | 心跳永不启动 → 约 30 秒后被服务器断线；消息分发/重连 handler 永不挂载 | `DouyuAutoJoinBarrageServerHandler`：LOGIN_RES 即启动心跳并切换 pipeline（幂等 `heartbeatStarted` 标志），pingreq/mrkl 保留为兼容触发 |
| 2 | 握手完成后 `String.format(getLogin(), roomId)` 对推送连接**已格式化**的 login 二次 format | login 报文任一字段含 `%` 时抛 `IllegalFormatException` 或错误替换 | `DefaultPushMessageType` 新增 `loginPreFormatted` 标志，推送连接已格式化则直接发送 |
| 3 | pipeline 切换后从已移除 handler 的 ctx 继续 `fireChannelRead` 不会送达消息（Netty 语义），老代码靠切换前的静态 dispatch 兜底 | 若触发消息只靠 fire 分发会丢失（监听器收不到 loginres） | 触发消息改用显式静态 `messageDispatch` 分发，不依赖 fire |

**实测验证（2026-10-29，单连接 100 秒）**：loginres 送达监听器 ✓；心跳在 loginres 后 100ms 内首跳且服务器响应 ✓；此后每 30 秒一跳、每次均有响应（3 次/100 秒）✓；全程连接存活 ✓。

审计确认无问题的点：`defaultPushMessageType()` 返回 clone（无单例污染）；拉流单例不被 setLogin 污染；心跳 30s + 新格式；vk/rt 同秒；h5ckreq 假 `ti` 服务器接受（无副作用，保留兼容）；keeplive tick 为秒级时间戳。

**遗留说明**：网页版对 loginres 前发送的弹幕有 100 条缓存（`sendCacheMessage`，loginres 后 flush）；本库不做缓存，调用方应在收到 `loginres`（或首个消息回执）后再 `writeAndFlush(pushMessage(...))`。
